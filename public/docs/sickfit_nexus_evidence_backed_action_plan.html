Main Problem From Feedback

The current issue is not that SickFit Nexus lacks data. The issue is that the data is presented like a database instead of an operations tool. Paden repeatedly says he does not know where to look, does not know what he is looking at, and cannot quickly understand what action to take.

Core direction: Rebuild SickFit Nexus around clear operations decisions, not raw data. Every page should show the account or product name first, explain the current status in plain English, and make the next action obvious.

The app needs to quickly answer:

  1. What needs my attention right now?
  2. What products are low, oversold, or at risk?
  3. What orders are active, delayed, draft, paid, fulfilled, or shipped?
  4. What manufacturing/restock orders are coming in and when?
  5. What can SickFit send to airport/store accounts as a lookbook or order tool?

Important Interpretation Rules

These rules prevent the plan from overreaching beyond what the transcript actually says.

Direct Transcript Instruction

Use these when Paden clearly asked for something. Example: replace Request with Draft, make status clickable, show the actual product instead of Shopify ID, and put LawsuitHoustonCentral at the top as the title.

Reasonable Inference

Use these when Paden described confusion but did not prescribe the exact UI solution. Example: using status badges, summary cards, and simplified tables is an inferred design solution to his repeated feedback that the app is too much and hard to digest.

Corrected PO Recommendation

Do not globally remove the term PO. Paden seemed okay with POs in some contexts, but he disliked confusing labels like RetailerPO, ManufacturerPO, and PO20000 as the main title. The better recommendation is to keep PO where useful, clean up the wording, and improve title hierarchy.

Priority 2: Clean Up Inventory Management

Inventory is one of the most urgent sections because Paden directly said Inventory Management is crucial before peak season and airport deals. The current inventory view is not clear enough for forecasting or operations.

Recommended Inventory Table

Inventory Definitions

  • Current Stock: what SickFit physically has right now.
  • Committed: units already promised to open orders.
  • Incoming: units expected from manufacturing/restock orders.
  • Available After Incoming: current stock + incoming - committed.
  • Status: plain-language inventory health.

Action Items

  • Add CSV/import support or clarify existing import flow.
  • Show manufacturing/restock orders inside inventory forecasting.
  • Use clear product names before Shopify IDs or SKUs.
  • Explain negative inventory as oversold, not just a raw negative number.
  • Reduce long text explanations and use scannable inventory fields.

Timeline

Week 1–2: Redesign the inventory table, add readable product names, add status badges, and start connecting incoming manufacturing quantities to inventory.

Done When

Paden can answer how many socks are physically available, what is oversold, what needs reorder, what is coming from manufacturing, and whether incoming manufacturing covers open orders.

Priority 3: Redesign PO Pages Without Over-Correcting PO Language

The transcript does not prove that all POs should be renamed to Customer Orders. It does show that the PO pages are visually overwhelming, that Request should be changed to Draft, that account/store names should be the main title, and that raw terms like RetailerPO and No Buy are confusing.

Corrected recommendation: Keep PO where it makes sense, but clean up technical labels. Use Retailer PO or Store PO if the order is from a retailer. For manufacturing, consider Manufacturing Order or Restock Order because Paden directly said he does not want manufacturing to be called a PO.

Priority 4: Fix Manufacturing Flow

Manufacturing is currently confusing because it feels like another PO area and does not show the details needed for forecasting. Paden specifically mentioned payment, ordered date, expected shipment, and the need to forecast.

Recommended Naming

Current Recommended Reason
ManufacturerPO Manufacturing Order Cleaner than raw camel-case and less confusing than a generic PO.
Manufacturing Pulse Manufacturing Incoming or Production & Restock Paden directly said he has no idea what Manufacturing Pulse means.
Create New PO inside Manufacturing Create Manufacturing Order / Create Restock Order Paden said he does not want this to be called a PO in the manufacturing context.

Manufacturing Order Fields

  • Manufacturer name
  • Products ordered
  • Quantity ordered
  • Ordered date
  • Payment status: Unpaid, Deposit Paid, Paid
  • Expected shipment date
  • Expected arrival date
  • Current status: Draft, Ordered, Paid, In Production, Shipped, Received, Delayed
  • Inventory impact / forecast impact

Inventory Connection

When a manufacturing/restock order is marked as received, the system should either update inventory automatically or prompt the user to confirm the inventory increase.

Timeline

Week 2–3: Rename manufacturing UI, redesign the manufacturing order form, add payment/order/shipping/arrival fields, and connect manufacturing to inventory forecast.

Done When

Paden can open manufacturing and clearly see what has been ordered, what has been paid, what is in production, what is delayed, what inventory is coming, and when it should arrive.

Priority 5: Finish Lookbook Flow for Airport Accounts

Lookbooks are critical because Paden directly connected them to upcoming airport accounts. The app needs to clarify whether a lookbook is a link, a preview, a PDF, or an ordering tool.

Recommended Lookbook Flow

  1. SickFit creates a lookbook for a specific account.
  2. The lookbook includes selected products/packs.
  3. SickFit can preview the lookbook.
  4. SickFit can export it as a PDF.
  5. SickFit can copy or share a public/private link.
  6. The customer selects products.
  7. The selected products generate a Retailer PO / Store PO / order record.

Required Lookbook Buttons

Preview Export PDF Copy Share Link Create PO from Lookbook Edit Products

Timeline

Week 3–4: Add PDF export, clarify the preview/share flow, and connect selected lookbook products to the PO/order system.

Done When

SickFit can confidently send a lookbook to an airport/store account and use it to generate an order.

Evidence: E15 E17

Priority 6: Reduce Visual Overload Across the App

This is a cross-page requirement. Paden’s repeated feedback is that the app has too much going on, relies on unclear titles, and gives him text or numbers that he does not digest.

UI Rules

  • Use plain-language headings.
  • Show product names before IDs.
  • Show account/store/manufacturer names before PO numbers.
  • Hide advanced metadata until expanded.
  • Use badges for statuses.
  • Use action-focused buttons.
  • Reduce long tables where possible.
  • Use summaries before details.
  • Avoid internal database language.
  • Every page should answer: “What am I supposed to do here?”

Recommended Page Structure

  1. Page title
  2. Short explanation
  3. Key summary cards
  4. Main table/cards
  5. Actions
  6. Advanced details only when expanded
